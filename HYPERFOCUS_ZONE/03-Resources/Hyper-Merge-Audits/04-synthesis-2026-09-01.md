## 1. The three documents are not the same kind of thing

They are often read as three takes on one question. They are three different questions, on three
different evidence bases, and that is the single most important thing to hold onto.

| | Deep-dive | Counter-audit | Academic report |
|---|---|---|---|
| **Question** | What exists across the repos? | What actually runs? | How should this be organised as a research programme? |
| **Evidence basis** | File and folder inventory of 5 repos | Clones read at a pinned HEAD + `gh` check history | GitHub profile, public repo list, health reports, `WHATS_DONE`, commit messages ([cite] markers) |
| **Epistemic reach** | Presence of files | Behaviour of code and CI | Stated intent in docs and commits |
| **Strongest section** | Ecosystem map, doc-culture read | §5 safety gate, §2 CI state | Operating model: tiers, evidence labels, canonical docs |
| **Blind spot** | Can't see whether anything works | Didn't cover org/narrative/funding | Reads intent as achievement — inherits the docs' optimism |

The deep-dive and the academic report both read the **documentation** of a system with an
unusually strong self-documentation culture. The counter-audit read the **system**. When the
first two disagree with the third, it is almost always because a doc describes a direction the
code has not finished travelling.

## 2. Where all three agree — treat as settled

These survive every evidence basis. Highest confidence in the whole set.

- **The engineering loop is real and visible.** Idea → build → test → break → document → harden.
  All three call this the core asset. The counter-audit adds a receipt: the safety-card commits
  (`card (a) — per-agent strict dispatch client`, `card (b) — dispatch capability registry`,
  `card c safety checks`) land on `main` 2026-08-31, the day after `academic-assessment` rev2,
  and close the exact gap rev2 named. Post-dates the critique and answers it.
- **Honest failure documentation is a genuine strength.** CI outage chains, the out-of-scope
  subagent incident, billing locks — all preserved in `WHATS_DONE`, not buried.
- **Canonical truth is distributed and it's a problem.** Deep-dive calls it "fragmented";
  academic report calls it "distributed"; counter-audit puts a number on it: **~1,984 tracked
  `.md` files, 124 handover/status/health docs across five repos**, and the audit chain itself
  is now six unlinked documents.
- **Superlatives need evidence labels.** "World's first", "AI agent army", "professional-grade".
  The academic report flags this *and then uses "neurodivergent-first autonomous AI
  infrastructure ecosystem" in its own executive statement* — the tension is live even inside
  the document raising it. rev2 §5.7 said the same. Retire or scope them.
- **CI must become a proof mechanism, not a local convenience.** All three. They differ only on
  how bad it is right now (§3).

## 3. Where they conflict — adjudicated

### 3.1 CI: "a concern" vs "a past outage" vs "red right now"

- Deep-dive: "CI and quality-gate reliability" is a thing to tighten.
- Academic report: "HyperCode's documented CI outage means not every protective workflow was
  reliably executing" — past tense, hedged, sourced from `WHATS_DONE`.
- Counter-audit [B, verified 2026-09-01]: `gh run list --branch main --limit 20` →
  **all 20 most-recent runs `failure` at `0s` duration**, and a targeted check of
  `agent-safety.yml` shows **all 6 of its runs on `main` `failure` at 3–5s** — the workflows
  trigger but never execute. Not "not every workflow" — every workflow, on every push to `main`,
  today.

**Adjudication:** the academic report understates a live, total outage as a resolved incident,
because `WHATS_DONE` describes the *diagnosis* and the report trusted it as the *state*. The
counter-audit is right. This also refutes the academic report's implicit claim that
`agent-safety.yml` keeps dispatches "independently testable" — it runs and dies in 3–5 seconds
without executing the suites.

### 3.2 Safety: "becoming structural" vs "enforces nothing by default"

- Academic report §"Safety is becoming structural": "fail-closed behaviour for mutation-capable
  paths", "deny-first routing", presented as current posture.
- Counter-audit §5 [A]: `test_safety_gate.py` *certifies fail-open*; both compose files ship
  `SAFETY_SHEPHERD_MODE=monitor`; in monitor mode `_safety_check_dispatch` returns "proceed" for
  **every** verdict, including a clean BLOCK from a healthy Shepherd. The fail-closed
  `safety_client` runs in **shadow only** — verdict logged, never acted on
  (`main.py:561` comment).

**Adjudication:** both are describing the same code from different distances. The *design* is
deny-first and fail-closed (academic report, correct about direction). The *shipped default
behaviour* is observe-only with a clean BLOCK ignored (counter-audit, correct about state). The
honest sentence is: **"the fail-closed dispatch path is built, contract-tested, and running in
shadow; it is one config flip and one `main.py` change from being load-bearing, and until then
agent dispatch is ungated in the default configuration."** Neither document says exactly that;
the synthesis should.

### 3.3 SDK ↔ course spec: unmentioned vs "actual divergence"

- Deep-dive: alignment "not yet exposed in one canonical spec" — flagged as unclear.
- Academic report: not mentioned.
- Counter-audit §4 [A]: full `diff` — the SDK `hyper-agent-spec.json` is a **superset**. It
  carries a `web3`/dNFT capability block, `badges`, and an `if/then` port rule that the course
  copy lacks entirely. The course spec is a stale fork that **cannot express a Web3 agent**.

**Adjudication:** the deep-dive's instinct was right, the academic report missed it, the
counter-audit has the receipt. This is a real reconciliation, not cosmetic.

### 3.4 meta-research-architect: "observe-only mode" vs rev2's runtime finding

- Academic report: "observe-only mode", distributing briefs to Redis/Discord/Obsidian.
- rev2 [B]: at the time it was checked, it was POSTing hourly to a **dead Discord webhook
  (HTTP 404)** with `RESEARCH_UPDATE_INTERVAL=3600`, plus 8 enumerated scaffold crash bugs and a
  compose `build:` context pointing at a nonexistent path.

**Adjudication:** "observe-only mode" is the intent. Its verified runtime state (as of rev2) was
broken. Not re-checked at HEAD `8839ae1b` — carry as **open**, not resolved.

## 4. The meta-finding

Across CI, safety enforcement, and the research agent, the two documentation-based reviews
(deep-dive, academic report) read **more favourably than the code supports, and in the same
direction each time** — plus a fourth gap, the agent-spec divergence, that both simply missed.
That is not sloppiness — it is structural. When a
system documents its intentions this thoroughly and this honestly, an audit of the documentation
measures the *quality of the intentions*, which here is genuinely high. It does not measure
whether the intention shipped.

This is the counter-audit's "diagnosis is not wired to enforcement" gap, observed one level up:
**even the audits inherit it.** The deep-dive and academic report describe a platform that is
substantially the platform's own roadmap. The counter-audit describes a platform where the
roadmap is real and mostly built, and the unfinished part — the flip from `monitor` to
`enforce`, the CI that would prove it, the spec reconciliation — is exactly the part that turns
"documented" into "true".

## 5. What the academic report adds that the other two don't

Credit where due — this is the section the counter-audit did not cover and the deep-dive only
gestured at. All three should be adopted:

- **Repository tiers** (Core / Active satellite / Archive). The 90-public-repo sprawl is a real
  discoverability tax; a machine-readable register fixes it.
- **A single evidence-status vocabulary.** Adopted, in the collapsed form below — one scale, not
  a third taxonomy on top of the report's `OBSERVED…HYPOTHESIS` and rev2's provenance `A–E`.
- **Six canonical documents** in one home. Sound. Priority order below.
- **The 30-day roadmap** is well-sequenced (legible → proof paths → whitepaper → bulletin).
  Its Week 2 ("confirm the agent safety workflow runs on pull requests") is currently blocked by
  §3.1 — that has to be Week 1, day 1.

### 5.1 Canonical evidence scale (adopt everywhere)

| Grade | Meaning |
|---|---|
| **A** | Live and independently verified |
| **B** | Automated-test verified |
| **C** | Implemented but not wired into the load-bearing path |
| **D** | Documented intention or scaffold |
| **E** | Known failure, outage, or unresolved risk |

This is a **capability-status** scale — what state is the thing in — which is the axis the
`EVIDENCE_LEDGER` needs. It is distinct from rev2's provenance markers (how a fact was
established: artifact / runtime / clone-read / doc / open); where the counter-audit writes
`[A]`/`[B]` inline it means the latter. Keep one status scale; don't multiply it.

Worked examples against current findings:

| Item | Grade | Why |
|---|---|---|
| HyperCode CI health | **E** | 20/20 recent `main` runs fail at `0s`; `agent-safety.yml` 6/6 fail at 3–5s |
| Strict fail-closed safety client | **C** | Built + contract-tested, but shadow-only — not on the load-bearing path |
| Safety contract tests | **B** | `assert_strict_client_contract` passes against the client |
| `safety_gate` in `monitor` default | **E** | A genuine BLOCK is logged and ignored |
| meta-research-architect | **C / D** | Implemented; runtime unverified (dead webhook + 8 scaffold bugs at last check) |
| SDK ↔ course `hyper-agent-spec.json` | **E** | Real divergence — course copy cannot express Web3 agents |
| Repository documentation culture | **B / D** | Strong and consistent, but documents intent, not runtime behaviour |
| The engineering / self-audit loop | **A** | Directly observed: rev2 critique → card commits on `main` the next day |

## 7. Scope limits of this synthesis

- No new code was run. This reconciles three existing documents against the counter-audit's
  already-verified findings at HEAD `8839ae1b`.
- The academic report's profile-level claims (90 public / 9 private repos, the wider
  constellation inventory) are taken as stated — not independently checked.
- BROskiPets and HyperAgent-SDK CI pass/fail state remains **open** — never run-checked.
- Everything the counter-audit listed as class E stays class E here.
- **None of this chain is committed.** `HperCore/` is not a git repository and is not inside
  one; all six audit documents (`Hyper Merge Deep-Dive Audit…`, `hyper-merge-audit-2026-09-01`,
  `hyper-merge-github-academic-report-2026-09-01`, this file, `academic-assessment-hypercode`
  ×2) are loose files there. Treating any of them as "the canonical source" requires committing
  them somewhere first — see action 9.

## 8. Bottom line

Three reviews, one system, and they only look contradictory. The deep-dive mapped it, the
academic report proposed how to run it as a research programme, and the counter-audit measured
what currently executes. Put together:

**Hyper Merge has a high-quality roadmap, a real self-correcting engineering culture, and a
running system that trails its own documentation.** The gap is concentrated and nameable: CI
that starts, a safety gate off `monitor`, one agent spec instead of two, one index instead of
~2,000 documents. The academic report's organisational moves are the right medium-term
programme. The counter-audit's items 1–3 are the right this-week programme. Do the second
first.

The defensible framing for any external reader — sponsor, collaborator, academic partner:

> Hyper Merge demonstrates unusually strong documentation, systems thinking, and
> safety-oriented design. Its current **runtime assurance is lower than its documentation
> maturity suggests**. The next phase is not more building — it is converting documented
> intention into continuously verified guarantees.

That gives the project real credit and states the one thing a credible audit must: the
distance between *"the system has a safety architecture"* and *"the system enforces safety"*.
Closing that distance is the central finding of all three reviews put together.
